WebView header regression: Chromium HeadersComplete generates Content-Length and Content-Type from Seek and the MIME value, then WebResourceResponse::GetResponseHeaders appends application headers. The WebView-only adapter now removes these two application header fields, so native generation produces a single value. For each simulated Chromium response the tests assert no duplicate application header, a single generated length, and exact equality with actual delivered body bytes.

WebView response contract:
- Valid 206: original Content-Range and CORS preserved; exact requested interval and length verified; initial native seek acknowledged without consuming response bytes; one correct generated Content-Length.
- Original request has Range but origin replies 200: explicit HTTP 502, readable empty body, generated Content-Length 0; local diagnostic event retained.
- Original request has Range and response is an error (including 403/416/504): original status retained, readable empty body, generated Content-Length 0; stale encoding/digest headers removed.
- No Range: known full Content-Length is supplied as the native initial available value; original body preserved with one exact generated length, including useful error text.
- Unknown body length, inconsistent Content-Range/Content-Length, or representation total beyond the native signed-int available limit: explicit 502 instead of unverifiable bytes.
- Plain string HTTP overload keeps original HTTP status, headers, and body semantics.
